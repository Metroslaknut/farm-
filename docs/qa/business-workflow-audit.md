# FARM+ — End-to-End Business Workflow Audit

**Run date:** 13 Oct 2026 (Asia/Bangkok)  
**Scope:** implemented API-to-database workflows, plus Web browser journeys. Synthetic users and throw-away MongoDB only. No production database, customer data, real payment/payout, email, SMS, video or AI provider was used.  
**Execution:** API suite `services/api` Vitest: **45 files, 1,021 tests passed**. Browser suite `e2e`, local Chrome: **11 passed** after adding a reviewer approval journey and direct MongoDB persistence checks. E2E TypeScript check passed. API and browser suites required loopback permission for isolated MongoDB and local server processes. Browser tests used `E2E_CHROME=1` because bundled Chromium was absent.

## How to read this report

Rows with PASS identify existing automated tests and the layer they actually exercise. API tests send requests through Express/services into a disposable MongoDB; they do not establish that every Web or Mobile control is wired correctly. UI/API/database journeys have separate evidence. NOT RUN means no corresponding executed scenario was found; BLOCKED means an external provider or deployed environment is required. An initial new browser test exposed a false-positive name assertion and test assumptions about badge casing and persisted field names; these were corrected. No product defect requiring a code fix was confirmed. Existing risks and deployment limits are summarized at the end.

For compactness, a row groups cases only where the preconditions, expected behavior, and evidence are materially the same. Test case names in the evidence column are searchable in the referenced file. Severity is the severity of an observed defect; for PASS/NOT RUN rows it is `—` (not an asserted risk rating).

### Scope decisions from source inspection

- **Subscriptions:** `subscriptionStatus` exists on the user model and is displayed by the admin user detail page. Shared types describe it as a field for a future billing module. There is no subscription model, billing route, renewal job or subscription payment flow. Subscription purchase/renewal/cancellation is therefore **NOT IMPLEMENTED**, excluded from pass counts, and not a testable workflow.
- **Payment provider:** `.env.example`, `packages/config/src/server.ts` and `modules/finance/provider.ts` confirm `none` disables online payments and `mock` is development/test-only; no production adapter ships. An official provider sandbox test is **BLOCKED BY MISSING IMPLEMENTATION**, not merely missing credentials.
- **Admin payment decision:** admin finance can read payments and reconcile; it has no manual payment approve/reject endpoint. Refunds have `approve/retry`; withdrawals have `approve/reject/retry`. Those are distinct implemented workflows. No manual payment approval/rejection result is claimed.
- **Registration entry:** applicant submission is an authenticated API route. The Web/Mobile apps have reviewer pages, but source search found no applicant registration form. The browser approval test seeds its application through the API, then exercises reviewer UI and applicant farm creation.
- **Atlas:** production MongoDB URI support is present, but no deployed Atlas cluster/account was configured for this run. All persistence assertions use the E2E disposable MongoDB.

## Coverage gaps and known limits

- Previously limited scenarios called out in this report: **A-09 is now PASS** for farm-owner approval via admin browser UI, subsequent applicant farm creation and direct DB verification; **C-04 remains PARTIAL** (no Web video upload/retry journey or real provider); **C-07 is BLOCKED** (no real Cloudflare account/credentials); **F-07 is BLOCKED** (no production payment adapter exists, so an official payment sandbox cannot be configured); **G-05 is BLOCKED** (no AI provider credentials); **I-05 remains NOT RUN** (no dashboard CSV download journey).
- The browser suite exercises sign-in/admin denial, MFA reviewer approval, farm creation/isolation, weight entry/history, community post/feed, shop purchase/payment, chat/notifications, and the marketplace offer-to-delivery journey. It does not drive every admin, moderation, media, wallet, analytics, refund, role-editor or shipment UI.
- Most scenario coverage is API → service → disposable MongoDB integration rather than UI → API → MongoDB. Those PASS results establish server behavior only where explicitly labeled. The E2E database checks below use `mongodb-memory-server`; **no MongoDB Atlas persistence, indexes, network policy, backup/PITR or cluster failover was verified**.
- Finance used only the in-memory mock provider. No official sandbox credentials were supplied, and the project has no real payment provider adapter. Video and AI adapters were also not exercised against external providers. Real SMS/email delivery, deployed staging, multi-instance behavior, mobile-device workflow execution and independent penetration testing were not run.
- Partial refunds are not supported. A mismatched amount/currency callback is rejected and left for reconciliation.
- This audit run found no newly confirmed failing defect, so no code change was warranted. The previously maintained [full system audit](full-audit-report.md), [security audit](security-audit.md), [financial test cases](financial-test-cases.md), and [risk register](risks-and-limitations.md) contain earlier findings, their fixes and residual deployment risks; they are not a substitute for the run results above.
