## 3. Cross-platform requirements

Evidence: `services/api/test/acceptance/cross-platform.test.ts` (10 tests) plus the web, mobile and e2e suites.

| Requirement                                            | Result                                                            | Evidence and limits                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

The same server returns the same figures to both                                                                                                                                                                           |
| Shared APIs behave consistently                        | **Pass**                                                          | the very client both apps use was driven against a real server: typed errors (`INVALID_CREDENTIALS`, `VALIDATION_ERROR` with field paths, 401/403/404) are identical for every caller                                                                                                                                                                                                                                                                                        |
| Authentication and authorization consistent            | **Pass**                                                          | one token model; permissions decided server-side on every request; silent refresh retries a rejected call **once** and never re-runs a state change (verified: one post, not two); a failed refresh ends in a 401 without looping; a second device does not disturb the first; revoking one session leaves the other                                                                                                                                                         |
| UI consistent with each platform's design system       | **Partially verified**                                            | each app has its own token/theme tests (web design tokens; mobile theme) and they pass. **No visual-regression or device review was performed.** Observation: the two design systems use different brand colours (web green, mobile red) — a product decision, not a defect, but worth confirming                                                                                                                                                                            |

## 5. Not tested in this environment

- **Mobile on a device or simulator.** Only the mobile unit tests (155) and the shared-client contract tests ran. Mobile navigation, camera/picker, push, deep links on a real OS, secure storage on a real keychain and playback performance are unverified.
- **A real payment provider** (none is implemented), real carrier rates (`SHIPPING_PROVIDER=none` — only seller-defined rates), a real streaming provider, a real AI model call (mock only; the Anthropic adapter has never run against the live service).
- **Any deployed environment**: no staging, no TLS/proxy/WebSocket routing, no Atlas backup/PITR restore drill, no alerts, no CDN. The Dockerfiles, GitHub workflows and EAS builds were never executed.
- **Browsers other than Chrome**, accessibility audits, internationalisation of the full UI, large-scale load, multi-instance behaviour.
- **Admin-console journeys with MFA in the browser** (the API-level admin steps are covered).

## 7. Unresolved issues and conditions for production

Gates (must be resolved or consciously accepted before public launch):

1. **Staging deployment and its verification** (`scripts/ops/verify-deployment.mjs`, restore drill, alerts) — not done. See [../ops/](../ops/README.md).
2. **Payments:** no real provider. Either build and sandbox-test an adapter (with legal/provider review) or launch with payments disabled and say so.
3. **Independent security review / penetration test** — not done ([../qa/risks-and-limitations.md](../qa/risks-and-limitations.md), R1).
4. **Malware scanning / file-content strategy** — written, not implemented (R2).
5. **Account deletion and data export** — missing; required by both app stores and PDPA (R4).
6. **Mobile:** device/simulator test pass, store listings, privacy forms, universal-link hosting, EAS build verification.
7. **Realtime scaling:** Redis adapter before more than one API instance (R6).
8. **Real-provider validation** for shipping rates, video streaming and AI (adapters exist or are mocked; none exercised live).

Accepted limitations (documented): partial refunds unsupported; content creation not idempotent; per-instance rate limits and caches; refresh token in `sessionStorage` (mitigated); inline styles allowed in the CSP; every authenticated request costs four reads (deliberate immediate revocation); no coverage percentage measured; load numbers are from an in-memory database on one machine.

## 8. Deployment readiness statement

- **Ready for:** a staging deployment, user-acceptance testing by the business, a security test engagement, and mobile device testing.
- **Not claimed:** production readiness. The platform behaves correctly across the tested end-to-end workflows with mock providers; whether it is ready for real money, real users and real traffic has to be established by the gates above.
- **Recommended next steps, in order:** (1) deploy to staging with the release workflow and attach the verification script output; (2) run the Atlas restore drill; (3) commission the penetration test while (4) building the account-deletion flow and the malware-scanning pipeline; (5) device-test the mobile app; (6) decide the payment launch strategy and, if payments launch, integrate and sandbox-test a provider using the journey and `test/qa/financial-qa` as the template; (7) re-run this whole acceptance suite against staging before go-live.
